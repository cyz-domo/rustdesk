## 一、 原理与架构介绍

### 1.1 为什么需要 STUN 适配？
官方标准的 RustDesk 服务端（`hbbs`）通常部署在拥有固定公网 IP 的云服务器上，其 **21116 端口同时处理 UDP 注册与 TCP 信令交互**。

而在家庭宽带（NAT1 / Full Cone NAT）环境下使用 **Lucky STUN 打洞** 时，一条 STUN 规则只能绑定单一协议（TCP 或 UDP），导致公网映射出来的端口互不相同：
- `hbbs (21116 UDP)` 映射为 `公网 IP:端口 A`（用于心跳注册与 NAT 打洞）
- `hbbs (21116 TCP)` 映射为 `公网 IP:端口 B`（用于主控发起连接握手、修改 ID、WebRTC 信令）
- `hbbr (21117 TCP)` 映射为 `公网 IP:端口 C`（用于打洞失败时的中继转发）

### 1.2 架构拓扑
```
┌────────────────────────────────────────────────────────────────────────┐
│                        内网服务器 (NAS / PC / 软路由)                  │
│                                                                        │
│   ┌──────────────────────────┐         ┌──────────────────────────┐    │
│   │     hbbs (注册与信令)    │         │     hbbr (中继转发)      │    │
│   │  UDP: 21116  | TCP: 21116│         │        TCP: 21117        │    │
│   └──────┬─────────────┬─────┘         └────────────┬─────────────┘    │
└──────────┼─────────────┼────────────────────────────┼──────────────────┘
           │             │                            │
           ▼             ▼                            ▼
┌────────────────────────────────────────────────────────────────────────┐
│                        Lucky STUN 规则 (单协议打洞)                     │
│   【规则1】UDP 21116     【规则2】TCP 21116          【规则3】TCP 21117 │
│           │                     │                           │          │
│           ▼                     ▼                           ▼          │
│      公网端口 A            公网端口 B                  公网端口 C       │
│   (例: 171.x.x.x:24869) (例: 171.x.x.x:24439)     (例: 171.x.x.x:24867)│
└───────────┬─────────────────────┬───────────────────────────┬──────────┘
            │                     │                           │
            └─────────────────────┼───────────────────────────┘
                                  ▼
┌────────────────────────────────────────────────────────────────────────┐
│                   DNS 服务商 (Cloudflare / 腾讯云 / 阿里云)            │
│  Lucky WebHook 自动更新 TXT 记录：                                      │
│  "host=171.x.x.x:24869,tcp=171.x.x.x:24439,relay=171.x.x.x:24867"      │
└─────────────────────────────────┬──────────────────────────────────────┘
                                  │ 极速 UDP 53 解析
                                  ▼
┌────────────────────────────────────────────────────────────────────────┐
│                         RustDesk 客户端                                │
│   只需填入解析域名 (如 rd.example.com)，客户端全自动识别 3 个端口并分流    │
└────────────────────────────────────────────────────────────────────────┘
```

## 二、 服务端部署说明 (hbbs & hbbr)

在局域网内任意 Linux、NAS（如群晖、威联通、UNRAID）或 Docker 容器中运行 `hbbs` 和 `hbbr`：

```bash
# 启动 hbbs (注册/信令服务)
hbbs -r 0.0.0.0:21117 -k _

# 启动 hbbr (中继服务)
hbbr -k _
```
> [!NOTE]
> `-k _` 参数会自动在当前目录下生成一对密钥文件（`id_ed25519` 和 `id_ed25519.pub`）。
> 将 `id_ed25519.pub` 中的字符串复制出来，在后文客户端配置的 **Key（安全验证）** 输入框中手动填写。
> 出于安全考虑，TXT 记录已不再分发 key（TXT 是无签名通道，客户端不采用其中的 key 值）。若服务端未开启强制验证（不带 `-k _`），可跳过此步。

## 三、 Lucky STUN 打洞规则配置 (3 条隧道)

登录 Lucky 管理后台，进入 **STUN 内网穿透** 模块，创建 3 条规则：

### 规则 1：hbbs UDP 注册与打洞服务
- **规则名称**：`RustDesk-UDP`
- **穿透协议**：`UDP`
- **目标内网 IP**：你的 hbbs 服务器内网 IP（如 `192.168.1.100` 或 `127.0.0.1`）
- **目标端口**：`21116`

### 规则 2：hbbs TCP 信令与控制服务
- **规则名称**：`RustDesk-TCP`
- **穿透协议**：`TCP`
- **目标内网 IP**：你的 hbbs 服务器内网 IP（如 `192.168.1.100` 或 `127.0.0.1`）
- **目标端口**：`21116`

### 规则 3：hbbr TCP 中继传输服务
- **规则名称**：`RustDesk-Relay`
- **穿透协议**：`TCP`
- **目标内网 IP**：你的 hbbr 服务器内网 IP（如 `192.168.1.100` 或 `127.0.0.1`）
- **目标端口**：`21117`

## 四、 Lucky WebHook 动态维护 DNS TXT 记录

当家庭宽带公网 IP 变动或 Lucky 重启重新分配了公网端口时，Lucky 的 WebHook / 自动化任务会自动将最新连接信息推送到域名的 **TXT 记录** 中。

### 4.1 TXT 记录格式规范
```text
host=公网IP:UDP端口,tcp=公网IP:TCP信令端口,relay=公网IP:中继端口
```

| 参数 | 说明 | 示例 |
| :--- | :--- | :--- |
| `host` | **必须**。`hbbs` UDP 注册端口（STUN 规则 1） | `198.51.100.123:24869` |
| `tcp` | **必须 (STUN 场景)**。`hbbs` TCP 控制端口（STUN 规则 2） | `198.51.100.123:24439` |
| `relay` | **必须**。`hbbr` TCP 中继端口（STUN 规则 3） | `198.51.100.123:24867` |
| `online`| **可选**。`21115` 在线状态查询端口（若未映射可不填） | `198.51.100.123:24438` |
| `api` | **可选**。`21114` Web 控制台/API 端口 | `http://198.51.100.123:21114` |
| `key` | **已废弃**。客户端可解析但不再采用，公钥请在客户端手动填写 | — |

#### 实际 DNS TXT 记录样例：
```text
host=198.51.100.123:24869,tcp=198.51.100.123:24439,relay=198.51.100.123:24867,online=198.51.100.123:24438,api=https://rustdesk-api.yourdomain.com
```

### 4.2 WebHook 脚本推送示例 (以 Cloudflare / 腾讯云为例)
在 Lucky 的 STUN 规则配置中开启 WebHook，在触发变量中获取最新的公网 IP 和 Port：
- `#{RustDesk-UDP.ip}` 与 `#{RustDesk-UDP.port}`
- `#{RustDesk-TCP.ip}` 与 `#{RustDesk-TCP.port}`
- `#{RustDesk-Relay.ip}` 与 `#{RustDesk-Relay.port}`

通过 API 将 TXT 内容更新为：
```text
host=#{RustDesk-UDP.ip}:#{RustDesk-UDP.port},tcp=#{RustDesk-TCP.ip}:#{RustDesk-TCP.port},relay=#{RustDesk-Relay.ip}:#{RustDesk-Relay.port}
```

## 五、 RustDesk 客户端配置与使用方法

支持本特性的 RustDesk 客户端已内置全自动 DNS TXT 智能寻址引擎。

### 5.1 客户端配置步骤
1. 打开 RustDesk 客户端，点击 **ID/中继服务器**（网络设置）；
2. 在 **ID 服务器（ID Server）** 输入框中，直接填入配置了 TXT 记录的**域名**（例如 `rustdesk.yourdomain.com`）：
   - 不需要手动指定端口；
   - 不需要分别填写中继服务器 / API / 在线状态端口（解析器会自动提取填入）；
3. 若服务端使用了 `-k _` 强制验证，在 **Key** 输入框手动填入 `id_ed25519.pub` 的公钥（仅需一次，不会随 TXT 变化，也不会被解析覆盖）；
4. 点击 **确定** 即可。

```
┌──────────────────────────────────────────────┐
│ 网络设置                                     │
├──────────────────────────────────────────────┤
│ ID 服务器 (ID Server):                        │
│ [ rustdesk.yourdomain.com                  ] │
│                                              │
│ 中继服务器 / API: 留空 (自动从 TXT 提取)       │
│ Key: [ id_ed25519.pub 公钥，手动填写一次 ]    │
└──────────────────────────────────────────────┘
```

### 5.2 状态确认
配置保存后，主界面左下角将显示 🟢 **就绪 (Ready)**。

#### 远程连接时如何确认直连/中继：
- 远程桌面窗口顶部标签栏有状态图标：
  - 🟢 **纯锁图标（Direct Connection）**：代表 **P2P 直连**，鼠标悬停显示 `直连并加密连接 (Direct and encrypted connection)`，流量不经过服务器，低延迟无带宽瓶颈。
  - 🔄 **中继图标（Relayed Connection）**：代表 **走 hbbr 转发**，鼠标悬停显示 `中继并加密连接 (Relayed and encrypted connection)`。

#### 如何提升画面流畅度 (60 FPS / 120 FPS)：
- 进入 `设置` -> `显示` -> 勾选 `自定义画质与帧率`，将 FPS 滑块拖动至 **60** 或 **120**。
- 开启 `硬件加速 (NVENC / AMF / QSV)`，获得更流畅的高帧率控制体验。

### 5.3 中继会话自动升级直连

初次连接落到中继后，主控端会在后台周期性重新竞速打洞（默认首次延迟 30 秒，之后间隔指数退避、封顶 5 分钟，持续 2 小时后停止探测）。NAT 映射在会话期间可能变得可打穿，因此值得重试。

- 一旦探测到可用直连路径，客户端自动重连并切换为直连，期间约 1-2 秒黑屏，无需任何手动操作；为防止打洞结果抖动导致反复重连，每个会话至多自动重连 2 次。
- 服务端策略强制中继（policy relay）、勾选了该设备"使用中继"或代理场景的会话**不参与**升级。
- 相关选项（客户端 options 配置文件）：
  - `enable-upgrade-to-direct`：设为 `N` 可关闭自动升级（默认开启）。
  - `upgrade-probe-interval`：首次探测延迟秒数，默认 `30`。

## 六、 常见问题排查 (FAQ)

### Q1: 提示「连接注册服务器失败」或「Please try later(0)」？
- **原因**：检查 TXT 记录中是否包含了 `tcp=` 端口。Lucky 的 TCP 打洞端口与 UDP 打洞端口必须分开配置。
- **解决**：确保 TXT 记录中包含 `host=IP:UDP端口,tcp=IP:TCP端口,relay=IP:中继端口`。

### Q2: 宽带重新拨号导致公网端口变了，需要手动重启客户端吗？
- **不需要**。RustDesk 被控端内置了 DNS TXT 后台轮询机制。当 DNS 记录更新后，客户端会自动无感热重载并与新的公网端口握手。

### Q3: 修改客户端自定义 ID 时报错？
- 最新版本已统一将 ID 修改校验通道（`RegisterPk`）指向 `tcp=` 端口，下载最新客户端即可直接修改。

### Q4: 局域网内两台电脑连接会走公网打洞流量吗？
- **不会**。客户端内置局域网直连探测（Intranet Direct），在同一个局域网内发起连接时会自动通过内网 IP 直连，不消耗任何外网流量。
